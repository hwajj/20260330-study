# 케어네이션 통합돌봄 (app-dailycare) 면접

## 면접 Q&A

### Repository·데이터 계층

#### Q. `JobRepository`를 두고 UI가 API를 직접 호출하지 않게 한 이유는?

A. 일상돌봔 API는 목록·상세·지원자·결제 endpoint와 응답 shape가 제각각이고, housekeeper/care 앱에서 옮긴 UI는 **도메인 타입**(`JobDetail`, `CaregiverCard`) 기준으로 동작해야 해요. 컴포넌트가 `fetchJobDetail`이나 snake_case 필드를 직접 알면 API가 바뀔 때마다 페이지 전체를 고쳐야 합니다.

`JobRepository` 인터페이스 + `mapJob`으로 **API → UI 변환을 data 계층에 고정**했고, `REACT_APP_USE_DUMMY=true`면 `DummyJobRepository`로 API 없이 UI 검수가 가능해요. `useJobList`·`useJobDetail`은 repository만 부르므로 훅·페이지 코드는 안정적입니다.

근거: `src/domain/JobRepository.ts`, `src/data/createJobRepository.ts`, `src/data/http/HttpJobRepository.ts`, `src/hooks/useJobList.ts`

---

#### Q. 상세 API에 `users`가 없을 때 `fetchCaregiverList`를 추가 호출하는 조건과 실패 처리는?

A. housekeeper 상세는 users가 detail에 붙어 오는 경우가 많은데, 일상돌봄 detail만 오고 지원자 배열이 비어 있을 수 있어요. `HttpJobRepository.getDetail`에서 **users.length === 0** 이고 **applicantCount > 0 또는 hasApplicant**이면 `/v3_0/protector/housekeeper/my_page/job/applicant_user/{jobId}`를 한 번 더 호출합니다.

보조 API가 실패하면 catch로 삼키고 detail만 반환 — 상세·지도·일정은 보여 주고, 지원자 탭만 빈/대기 UI로 떨어지게 했어요. **핵심 화면을 지원자 API 실패로 막지 않기** 위한 fallback입니다.

근거: `src/data/http/HttpJobRepository.ts` 53~64행, `src/api/jobApi.ts` `fetchCaregiverList`

### 목록·React Query

#### Q. `useJobList`의 `keepPreviousData`와 `isError` 조건을 왜 그렇게 짰나?

A. HistoryPage는 `inprocess` ↔ `complete` 탭을 바꿀 때 filter가 `in_progress` / `closed` / `complete`로 바뀌고, **queryKey가 filter마다 달라요**. `keepPreviousData: true`면 새 filter를 fetch하는 동안 **이전 탭 목록을 그대로 보여 줘서** 빈 화면·깜빡임을 줄입니다.

`isLoading`은 `isLoading || (isFetching && isPreviousData)` — 캐시가 전혀 없을 때, 또는 이전 데이터를 보여 주는 refetch 중에만 로딩. `isError`는 **`query.isError && items.length === 0`** — 캐시가 남아 있으면 일시적 실패를 사용자에게 드러내지 않아요. 탭 왕복·네트워크 흔들림에서 UX를 우선한 선택입니다.

근거: `src/hooks/useJobList.ts`, `src/pages/HistoryPage.tsx`, `src/data/queryClient.ts`

---

#### Q. 결제 성공 후 `invalidateQueries`를 안 하면 어떤 문제가 생기나?

A. `queryClient` staleTime이 10초라서, 결제 직후 상세·목록을 다시 열면 **최대 10초 동안 apiStatus·결제 탭·「결제 정보 없음」 같은 결제 전 상태**가 캐시에서 나올 수 있어요. 사용자는 PG에서 돌아왔는데 아직 「결제 대기」로 보이는 불일치가 납니다.

`PaymentResultPage`에서 `code === 200`이면 `jobKeys.lists()`와 `jobKeys.detail(jobId)`를 invalidate해서 **다음 mount/refetch에서 서버 상태**를 받게 했습니다. 결제는 상태 전환의 핵심 이벤트라 staleTime을 믿지 않고 명시적으로 캐시를 버립니다.

근거: `src/pages/PaymentResultPage.tsx` 24~31행, `src/data/queryKeys.ts`, `src/data/queryClient.ts`

### 공고 상세·탭

#### Q. `resolveJobDetailTabs` — 공고 상태에 따라 탭이 어떻게 달라지나?

A. 규칙은 housekeeper JobDetailPage 이식 기준이에요.

1. **공고 닫힘** (`statusStr === '공고 닫힘'` 또는 `status === 'closed'`) → **가사지원 상세** 탭만.
2. **지원자 없음** (`!hasApplicant`) → **상세 + 지원한 케어메이트**.
3. **apiStatus ≤ 2** (매칭/결제 대기) → 역시 **상세 + 케어메이트** — 아직 선택·결제 단계.
4. 그 외(결제 이후 등) → **상세 + 결제 정보** — 케어메이트 탭은 빼고 결제 탭으로 합침.

`JobDetailPage`는 URL `?tab=`이 tabs에 없으면 `pickDefaultTab`으로 replace 동기화해서 잘못된 deep link를 막습니다.

근거: `src/components/jobDetail/jobDetailTabs.ts`, `src/pages/JobDetailPage.tsx`

---

#### Q. `DetailNotice`에서 「케어메이트에게 연락하기」가 노출·동작하는 조건은?

A. `isMatched`: `caregiverName`이 있거나 `apiStatus >= 3`이면 매칭 후로 봅니다. 매칭 전에는 지원·선택·결제 안내가 긴 유의사항, 매칭 후에는 문구를 줄이고 통화 버튼을 footer에 둡니다.

통화 클릭 시 `detail.hasPayment`이면 `tel:${caregiverPhone}`, 아니면 「결제 정보가 없습니다」 팝업 — **결제 완료 전 연락처 노출을 막는** guard입니다. payment 탭 footer는 결제 관련 필독 아코디언 + 동일 통화 버튼.

근거: `src/components/jobDetail/DetailNotice.tsx`, `src/domain/types.ts` `hasPayment`·`caregiverPhone`

### 결제

#### Q. 결제 흐름: 케어메이트 선택 → 주문 생성 → CI/REAL 분기를 설명해 주세요.

A. **선택**: `CaregiverProfileCard`에서 `paymentRepository.selectCaregiver(applicantId)` — 성공하면 `/dailycare/payment?id=&applicantId=`로 이동. 400/401은 blocked 메시지 팝업.

**결제 페이지**: `useJobDetail(id)`와 payer query로 공고·케어메이트·결제자 정보 로드. 「결제하기」 클릭 시:
- **0원** → `FreeMatchingPopup` → 확인 시 `createOrder(total:0)` → `redirectUrl`로 결과 페이지.
- **유료** → `createOrder` → `proceedPayment`:
  - **CI/QA** + `order.redirectUrl` → PG 없이 `navigate('/dailycare/payment/result?…')`
  - **REAL** → `submitGeneralPayment`로 Welcome PG 폼 submit (merchant·키·P_SIGNATURE)

**결과**: query string `code`·`jobId` 등 파싱, 성공 시 job 캐시 invalidate 후 공고 결제 탭 또는 목록으로.

근거: `src/components/jobDetail/CaregiverProfileCard.tsx`, `src/pages/PaymentPage.tsx`, `src/constants/payment.ts`, `src/pages/PaymentResultPage.tsx`

---

#### Q. `ordering` / `currentOrder` ref로 막는 중복 시나리오는?

A. **ordering**: `createOrder`·`submitFreeMatching` 진입 시 true — **연속 클릭·더블 탭**으로 주문 API가 두 번 나가는 것 방지. finally에서 false.

**currentOrder**: 첫 주문 성공 후 order 객체를 보관 — CI/QA에서 redirect 전, REAL에서 PG 팝업/폼 재진입 시 **같은 orderId로 다시 proceed**할 수 있게 함. 주문은 한 번만 만들고, 결제 UI만 다시 여는 패턴.

둘 다 PaymentPage 주석 「동시 호출과 결제수단 팝업을 다시 연 경우의 중복 주문 생성」 대응입니다.

근거: `src/pages/PaymentPage.tsx` 35~37행, 127~168행

#### Q. REAL 환경 PG 폼(`submitGeneralPayment`)에서 과세/면세 분기는 어떻게 하나?

A. `order.tax > 0`이면 과세 — REAL merchant `wpcaren20d`, 키 `REACT_APP_VAT_PAYMENT_KEY`. tax 없으면 면세 `wphmcnw20d` + `REACT_APP_VAT_FREE_PAYMENT_KEY`. CI/QA는 테스트 상점 `wphtest200` + `REACT_APP_TEST_PAYMENT_KEY`.

`P_OID` = merchantId + timestamp, `P_SIGNATURE` = sha256(`mkey=…&P_AMT=…&P_OID=…&P_TIMESTAMP=…`) — housekeeper와 동일 규칙 주석이 있어요. `P_NEXT_URL`·`P_RETURN_URL`은 `{orderId}` 치환된 callback template.

근거: `src/constants/payment.ts` 47~91행, `.env.example`

### 배포·API 규약

#### Q. `withStaticPath`와 `REACT_APP_ROUTER_BASENAME` — 로컬 vs 운영 정적 자산 차이는?

A. 라우팅은 항상 `/dailycare/...` Route path로 처리하고, **CRA homepage는 쓰지 않아요** — nginx가 빌드된 js 경로를 sub_filter로 치환하기 때문에 homepage에 prefix를 넣으면 **경로가 이중으로** 붙을 수 있습니다.

정적 자산(`/img/...`)만 `withStaticPath`로 env prefix를 붙입니다. 로컬 dev는 carenation static proxy가 referer로 `/img/`를 넘기므로 prefix 비움; 운영 `.env.production`에서는 `/dailycare` 설정. **라우팅 basename과 public asset prefix를 env로 분리**한 이유가 주석에 있습니다.

근거: `src/constants/basePath.ts`, `.env.example` 26~28행

---

#### Q. `apiRequest`가 care와 동일하게 `code === 200`만 성공으로 보는 이유와 `UserType: protector` 헤더는?

A. carenation 백엔드는 HTTP 200이어도 body `code`가 4xx/5xx면 비즈니스 실패로 처리해요. status code만 보면 「성공」으로 파싱했다가 UI가 깨집니다. 그래서 **json.code !== 200이면 ApiError** — care 앱과 같은 계약.

`UserType: protector`·`AppVersion`·`Authorization`은 보호자 앱 API 관례. 일상돌봄 job 목록도 `service_type: dailycare`, `job_type: dailycare` query로 protector job API를 호출합니다.

근거: `src/api/client.ts` 66~114행, `src/api/jobApi.ts` 47~57행

### 미연결·stub 범위

#### Q. `PaymentHistoryTab`의 보험·통화 stub과 실제 연동 범위는?

A. 결제 정보 탭 UI는 housekeeper 4-3.html 마크업 이식 — 매칭된 케어메이트 프로필, 달력·일시·총액, 결제자명·「결제 완료/결제 정보 없음」은 **detail API의 users·payerName·apiStatus**로 채웁니다.

**간병인배상책임보험** 링크는 `stubAction` → `window.alert('준비 중입니다. (결제·통화 API 미연결)')` — 보험 PDF/상세 API는 아직 없어요. 반면 `DetailNotice`의 `tel:` 통화는 `payment.cgs_user.phone`이 mapJob을 통해 `caregiverPhone`으로 온 경우 **실제 연동**입니다. PaymentResultPage 주석대로 **네이티브 branch/analytics**도 제외된 상태.

근거: `src/components/jobDetail/PaymentHistoryTab.tsx`, `src/components/jobDetail/DetailNotice.tsx`, `src/pages/PaymentResultPage.tsx` 11행
