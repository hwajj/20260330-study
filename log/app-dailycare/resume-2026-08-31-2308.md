# 케어네이션 통합돌봄 (app-dailycare)

## 한 줄 요약

보호자용 통합돌봄(가사지원) 공고 목록·상세·케어메이트 선택·결제를 `/dailycare` CRA SPA로 제공하고, Repository 패턴·React Query·환경별 PG 분기로 care/housekeeper UI를 이식·연동한 프론트엔드 작업.

## 기술 스택 / 역할 키워드

- React 17, TypeScript, Create React App (react-scripts 4)
- React Router 6, TanStack React Query 4
- fetch 기반 API 클라이언트 (care `code === 200` 규약)
- Welcome PG (`submitGeneralPayment`, SHA256 서명)
- nginx `/dailycare` 서브패스 배포, 카카오맵 (공고 상세 지도)

## 이력서 불릿

### 라우팅·배포 (`App.tsx`, `basePath.ts`)

- `/dailycare` 중첩 라우트로 login·history·jobs/:id·payment·payment/result를 묶고, `AuthGuard`로 보호 구간을 분리함.
- CRA `homepage` 필드는 쓰지 않고 Route path + `navigate('/dailycare/...')`로 라우팅 — nginx `sub_filter`가 static/js 경로를 치환하므로 빌드 산출물에 prefix를 넣으면 경로가 중복됨.
- `withStaticPath` + `REACT_APP_ROUTER_BASENAME`으로 운영만 public 정적 자산에 prefix를 붙이고, 로컬 dev는 carenation static proxy가 `/img/`를 referer 기준으로 전달하므로 prefix 없음.

### 인증 (`auth/`)

- `AuthGuard`: localStorage 토큰 없으면 `/dailycare/login`으로 replace 리다이렉트, `state.from`으로 복귀 경로 전달.
- `apiRequest` 401 시 `clearAuth` + 로그인 페이지 assign — care 앱과 동일한 세션 만료 처리.
- `LoginPage`는 API 검증용 테스트 로그인(이메일·비밀번호) — 보호자 `UserType: protector` 헤더로 care API 호출.

### 도메인·Repository (`domain/`, `data/`)

- UI는 `JobRepository`·`PaymentRepository` 인터페이스만 의존 — API 스펙 변경 시 `Http*` 구현체만 교체.
- `REACT_APP_USE_DUMMY=true`이면 `DummyJobRepository`로 목록·상세 UI 검수, false이면 `HttpJobRepository`로 실 API 연동.
- `mapJob`·`mapPayment`에서 care API의 status·cancel_status·applicant·payment 중첩 객체를 `JobDetail`·`JobListItem`·`CaregiverCard` UI 타입으로 변환.

### API 클라이언트 (`api/client.ts`)

- `REACT_APP_BASE_URL` 비우면 CRA proxy(`package.json` → ci_api)로 same-origin 요청, 있으면 절대 URL.
- `REACT_APP_CARE_API_URL` prefix로 `/v3_0/protector` 등 경로 분기 — job 목록·상세와 housekeeper 결제·지원자 API가 다른 prefix를 씀.
- HTTP 200 + body `code === 200`만 성공; `raw` 옵션으로 `redirect_url` 등 data 바깥 필드 수용.

### 통합돌봄 목록 (`HistoryPage`, `useJobList`)

- URL `?tab=inprocess|complete`로 진행/완료 탭 전환; 완료 탭에서 「완료 내역만 보기」 체크 시 filter를 `closed` → `complete`로 바꿈.
- `useJobList`: filter별 queryKey 분리 + `keepPreviousData` — 탭 전환 시 목록이 깜빡이지 않음.
- `isLoading`은 캐시 없을 때만, `isError`는 보여줄 캐시가 없을 때만 — 이전 필터 데이터를 유지하며 refetch 중에도 UX 유지.

### 공고 상세 (`JobDetailPage`, `jobDetailTabs`)

- `resolveJobDetailTabs`: 공고 닫힘 → 상세만; 지원자 없음 또는 status≤2 → 상세+케어메이트; 그 외 → 상세+결제(케어메이트 탭 제외).
- invalid/missing `?tab=`은 `pickDefaultTab` + `replace`로 URL 동기화.
- `JobDetailView`: 카카오맵(`ResultMap`), 선택 일자 달력(`ScheduleCalendar`), 가사지원 대상·장소·서비스 신청 내역 섹션.
- 상세 API에 `users` 없고 지원자가 있으면 `fetchCaregiverList` 보조 호출 — 실패 시 detail만으로 표시.

### 지원 케어메이트 (`AppliedCaregiverTab`, `CaregiverProfileCard`)

- 지원자 0명 → 「케어메이트가 지원할 때까지 대기」 대기 UI; 있으면 프로필 카드 목록.
- 「케어메이트 선택」 → `paymentRepository.selectCaregiver` → 성공 시 `/dailycare/payment?id=&applicantId=` 이동; 400/401은 blocked 사유 팝업.
- `buildCaregiverDetailUrl` + `window.location.href`로 기존 care 케어메이트 상세 페이지 이동; `useCaremateAward`로 수상 라벨 lazy 로드(staleTime ∞).

### 결제 (`PaymentPage`, `constants/payment.ts`)

- query `id`(공고)·`applicantId`로 jobDetail·caregiverCard·payerInfo 조회; `useJobDetail` 캐시를 상세 페이지와 공유.
- `ordering` ref로 동시 클릭·팝업 재오픈 시 중복 주문 생성 방지; `currentOrder` ref로 결제수단 팝업 재진입 시 재주문 없이 PG 진행.
- CI/QA: `redirectUrl` 있으면 PG 없이 `/dailycare/payment/result?` 로 이동; REAL만 Welcome PG 폼 submit(과세/면세 merchant·키 분기, SHA256 서명).
- 0원: API 없이 `FreeMatchingPopup` → 확인 시 `createOrder(total:0)` → redirect 결과 페이지.

### 결제 결과 (`PaymentResultPage`)

- query `code`·`jobId`·`name`·`amount`·`msg` 파싱; 성공(code 200) 시 `jobKeys.lists()`·`jobKeys.detail(jobId)` invalidate — staleTime 10s 동안 결제 전 상태가 보이는 문제 방지.
- 네이티브 branch/analytics 브릿지는 의도적으로 제외(housekeeper PaymentCompletePage 주석 기준).

### 하단 유의사항·통화 (`DetailNotice`)

- 매칭 후(`caregiverName` 또는 apiStatus≥3): 유의사항 문구 축소 + 「케어메이트에게 연락하기」 — `hasPayment`일 때만 `tel:` 링크, 없으면 팝업.
- 결제 탭 footer: 결제 관련 필독 아코디언 + 고정 하단 통화 버튼.

### 팝업 (`PopupContext`, `PopupWrap`)

- `PopupProvider` 전역 — `element`(커스텀 JSX) 또는 `content`(문자열) + `onConfirm`/`onCancel`.
- 닫힘 트랜지션 300ms 후 state 초기화 — exit 애니메이션 중 본문이 사라지지 않게 함.

### React Query 설정 (`queryClient.ts`, `queryKeys.ts`)

- staleTime 10s, refetchOnWindowFocus false, retry 1 — refetchOnMount `'always'`는 staleTime을 무시하므로 사용하지 않음.
- `jobKeys.lists()`로 status별 목록 캐시 일괄 무효화; payment payer·award는 별도 키.

### 네이티브 간편결제 (`constants/native.ts`)

- UA `connectionType/webview`로 Android `AndroidApp.easyPayment` / iOS `webkit.messageHandlers.easyPayment` 호출 — 서비스 구분값 `dailycare` 고정.
- 웹에서는 `'web'` 반환 — 간편결제는 앱 WebView 전용.

## STAR

### 1. Repository 패턴으로 UI와 care API 분리

- S: housekeeper·care 앱에 있던 가사지원 UI를 일상돌봄(dailycare) SPA로 이식해야 했고, API 응답 형태가 목록·상세·지원자·결제마다 달랐음. UI 개발 중 API가 바뀌거나 더미로 검수해야 하는 경우가 있었음.
- T: 컴포넌트·훅이 fetch 경로·필드명에 직접 의존하지 않게 하고, **실 API / Dummy를 env 한 줄로 교체**할 수 있게 만들기.
- A:
  - `JobRepository`·`PaymentRepository` 인터페이스와 `JobDetail`·`JobListItem` 등 UI 전용 타입을 `domain/`에 정의.
  - `HttpJobRepository`에서 `fetchJobList`·`fetchJobDetail`·`fetchCaregiverList` 호출 후 `mapJob`으로 변환; detail에 users 없을 때 지원자 API fallback.
  - `createJobRepository()` factory에서 `REACT_APP_USE_DUMMY` 분기; `useJobList`·`useJobDetail`은 repository만 호출.
- R: (코드 기준) pages·hooks가 `jobApi`/`paymentApi`를 직접 import하지 않고 repository 경유 — API·매핑 변경 지점이 `data/http/`로 모임.

### 2. 환경별 결제 분기 — CI/QA 우회 vs REAL PG vs 0원 매칭

- S: 결제는 CI/QA에서 PG 없이 redirect로 결과를 확인해야 하고, REAL에서는 Welcome PG(과세/면세 상점·키)로 실결제해야 함. 본인부담금 0원 공고는 PG 없이 매칭만 확인하면 됨.
- T: **환경·금액·재진입**마다 다른 분기를 PaymentPage 한 곳에서 안전하게 처리하기.
- A:
  - `getServerType()`·`isRealPaymentEnvironment()`로 CI/QA/REAL 판별; CI/QA + `redirectUrl` → navigate 결과 페이지, REAL → `submitGeneralPayment` 폼 submit.
  - `ordering`·`currentOrder` ref로 중복 주문·재팝업 시나리오 차단.
  - `totalFee === 0` → `FreeMatchingPopup` → 확인 후 `createOrder(total:0)`만 호출.
  - PG 폼 필드(P_OID, P_SIGNATURE, P_TAX 등)와 merchantId(wpcaren20d/wphmcnw20d/wphtest200)를 housekeeper와 동일 규칙으로 채움.
- R: (코드 기준) PaymentPage·payment.ts에 환경·0원·REAL PG 경로가 분리 구현됨; PaymentResultPage에서 성공 시 job 캐시 invalidate.

### 3. 공고 상태 기반 탭·하단 UX — 상세/케어메이트/결제 전환

- S: 공고 lifecycle(매칭 대기 → 지원 → 선택·결제 → 진행)에 따라 보여줄 탭과 하단 버튼(유의사항·통화)이 달라짐. housekeeper 마크업(4.html·4-3.html·5.html) 규칙을 코드로 옮겨야 했음.
- T: status·status_str·지원자 유무에 따라 **탭 노출·기본 탭·footer**를 일관되게 맞추기.
- A:
  - `resolveJobDetailTabs`·`pickDefaultTab`으로 탭 배열·URL `?tab=` 동기화; closed 공고는 상세만.
  - `DetailNotice`의 `isMatched`로 매칭 전/후 유의사항·통화 버튼 분기; 결제 탭은 payment 모드 전용 copy.
  - `CaregiverProfileCard`의 `showSelect`는 apiStatus 0< status <3일 때만 — 결제 대기 구간에서만 선택 버튼.
- R: (코드 기준) JobDetailPage·DetailNotice·jobDetailTabs가 care `JOB_STATUS` 숫자와 status_str을 공유해 탭·버튼 노출이 연결됨.
