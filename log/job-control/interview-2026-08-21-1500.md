# Job Control 면접

## Q&A

### 1. React Query `useMutation`을 쓴 이유와 `useQuery`를 쓰지 않은 이유

**Q.** 이 프로젝트에서 React Query를 쓰면서 `useMutation`만 사용했습니다. `useQuery`는 왜 쓰지 않았나요?

**A.**  
공고 생성·삭제는 사용자 버튼 클릭에 의해 발생하는 **쓰기(write) 작업**이고, 화면에 상시 노출할 **조회용 서버 상태 목록**이 없습니다. `page.tsx`에서 `createJobMutation`·`deleteJobMutation` 두 개의 `useMutation`으로 POST 요청을 감싸 `isPending` 로딩, `onSuccess`/`onError` 결과 처리, mutation 함수 재사용을 한곳에서 관리합니다.  
`useQuery`는 GET 기반 캐시·refetch에 적합한데, 이 앱은 단일 페이지 폼 UI이고 생성 결과는 mutation 성공 시 `createResult` 로컬 state에 JSON으로 표시하므로 query cache가 필요하지 않습니다. `providers.tsx`에서 `QueryClientProvider`만 전역으로 두고 mutation API만 활용한 구조입니다.

**근거:** `src/app/page.tsx`, `src/app/providers.tsx`

### 2. localStorage + SSR에서 Hydration mismatch를 어떻게 막았는가

**Q.** 토큰을 localStorage에 저장하는데 Next.js SSR과 충돌하지 않나요?

**A.**  
충돌을 막기 위해 **초기 state는 항상 빈 문자열**로 맞췄습니다. 서버 렌더와 클라이언트 첫 렌더 모두 `protectorToken=""`, `caregiverToken=""`이므로 HTML이 일치합니다.  
마운트 이후 `useEffect`에서만 `getStoredProtectorToken()` / `getStoredCaregiverToken()`으로 localStorage를 읽어 state를 갱신합니다. 코드 주석에도 「Hydration: 서버와 초기 클라이언트는 ''로 동일하게 맞추고, 마운트 후에만 localStorage 복원」이라고 명시되어 있습니다.  
토큰 변경은 별도 effect로 storage에 sync하며, `typeof window === "undefined"` 가드와 try/catch로 SSR·storage 비활성 환경을 처리합니다.

**근거:** `src/app/page.tsx` (PROTECTOR_TOKEN_STORAGE_KEY, useEffect 블록)

### 3. `postJob`의 NDJSON 스트림 파싱·버퍼 처리 방식

**Q.** 공고 생성 API 응답을 어떻게 실시간 진행률로 받나요?

**A.**  
`src/lib/job.ts`의 `postJob`은 `type`이 `soon` 또는 `in_progress`일 때 응답 body의 `getReader()`로 스트림을 읽습니다. `TextDecoder`로 chunk를 문자열에 이어 붙인 뒤 `\r?\n`으로 줄 분리하고, **마지막 불완전 줄은 buffer에 남겨** 다음 chunk와 합칩니다.  
각 줄을 `JSON.parse`하고, `progress` 문자열 필드가 있으면 `onProgress`를 호출합니다. `code` 필드가 있는 객체는 최종 결과(`lastData`)로 갱신합니다. 스트림 종료 후 buffer 잔여분도 동일하게 처리합니다. parse 실패 줄은 무시합니다.  
reader가 없으면(비스트림 응답) fallback으로 `res.json()` 한 번만 파싱합니다.

**근거:** `src/lib/job.ts` (create 분기, while read loop)

### 4. `soon` vs `in_progress` 클라이언트 검증 규칙 차이

**Q.** 간병예정과 진행중 공고의 날짜 검증이 UI에서 어떻게 다른가요?

**A.**  
`validatePayloadForCreate(kind, payload)`에서 분기합니다.

- **간병예정 (`soon`)**: `job_start_date`는 **현재 시각보다 이후**여야 합니다(`startMs <= nowMs`면 에러). `job_end_date` 형식 검증은 soon 분기에서 start만 엄격히 봅니다.
- **진행중 (`in_progress`)**: `job_start_date`는 **한국 시간 기준 현재 시 정각 이하**(`startMs > floorNowMs`면 에러). `job_end_date`는 **현재 시각보다 이후**여야 합니다.

비교에 `parseSeoulWallDatetimeMs`(벽시계 +09:00)와 `formatSeoulYmdHourFloor`(현재 시 정각)를 사용해 README의 「job_start_date는 현재 이후(soon) / in_progress는 DB 반영용 과거 시작」 규칙과 UI 문구를 맞췄습니다.

**근거:** `src/app/page.tsx` (`validatePayloadForCreate`), `src/lib/seoul-time.ts`, `README.md`

### 5. 시간제(term)와 기간제(day) 기본 페이로드 설계

**Q.** 시간제와 기간제 JSON 기본값은 어떻게 나뉘나요?

**A.**  
`src/data/defaultJobPayload.ts`에서 공통 `BASE_PAYLOAD`(주소, 환자, `care_info`, `contract_info` 등) 위에 일정 필드만 다르게 붙입니다.

| | term (시간제) | day (기간제) |
|---|---------------|--------------|
| `job_type` | `"term"` | `"day"` |
| `job_end_date` | 오늘 22:00 | 오늘+2일 20:00 (`addDaysSeoulYmd`) |
| `job_date` | `[today]` 배열 | `null` |

시작 시각은 `mode`: `soon` → `${today} 19:00:00`, `in_progress` → 1시간 전 정각.  
UI에서 term/day 토글 시 `buildDefaultPayloadString(type, createKind)`로 textarea JSON 전체를 교체해, 사용자가 수정하지 않아도 README 안내와 동일한 기본값으로 생성 가능하게 했습니다.

**근거:** `src/data/defaultJobPayload.ts`, `src/app/page.tsx` (토글 onClick)

### 6. `progress-config`의 `stepCount`와 progress bar·라벨 연동

**Q.** 진행률 바 퍼센트는 어떻게 계산하나요?

**A.**  
서버가 보내는 progress 키는 `"1.protector my-page"`처럼 **앞에 단계 번호**가 붙습니다. `parseCreateProgressStep`이 정규식 `^(\d+)\.`으로 숫자를 추출합니다.  
`getProgressConfig(activeJobService)`가 care일 때 `stepCount: 9`와 `progressLabels`를 반환합니다. progress bar width는 `(단계번호 / stepCount) * 100`%, `aria-valuenow`도 동일 비율입니다.  
표시 문구는 `progressConfig.progressLabels[createProgress] ?? createProgress`로, 설정에 없는 키는 raw 문자열 fallback입니다. `CARE_PROGRESS_LABELS`의 `{n}`은 `formatLabels`에서 `stepCount`로 치환되어 「1/9 …」 형태가 됩니다.

**근거:** `src/lib/carenation/progress-config.ts`, `src/app/page.tsx` (progressbar, parseCreateProgressStep)

### 7. 35초 타임아웃·삭제 `AbortError` UX 처리

**Q.** 긴 생성 요청이나 타임아웃은 UI에서 어떻게 처리하나요?

**A.**  
`postJob`은 모든 타입에 `AbortController`와 35�000ms `setTimeout(() => ac.abort())`를 걸고 `fetch` signal에 연결합니다.  
- **생성**: abort 시 mutation `onError`에서 `e.message`를 `createError`에 표시  
- **삭제**: `deleteJobMutation.onError`에서 `e.name === "AbortError"` 또는 메시지 `"The operation was aborted."`이면 사용자-facing 문구를 **「요청 시간 초과」**로 통일  

생성 중에는 `isCreating`으로 JobService select·만들기 버튼 비활성, `createProgress`로 단계 문구·바 표시. 성공 시 `setCreateProgress(null)`로 정리합니다.

**근거:** `src/lib/job.ts` (timeoutMs, AbortController), `src/app/page.tsx` (deleteJobMutation.onError, disabled states)
