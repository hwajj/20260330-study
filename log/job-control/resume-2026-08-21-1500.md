# Job Control

Carenation 간병 공고 생성·삭제를 테스트·자동화하기 위한 Next.js 단일 페이지 관리 UI.

## 스택

| 구분 | 기술 |
|------|------|
| 프레임워크 | Next.js 16 (App Router) |
| UI | React 19, TypeScript |
| 스타일 | Tailwind CSS 4 (`@theme inline`, oklch 토큰) |
| 서버 상태 | TanStack React Query v5 (`useMutation`) |
| 유틸 | clsx, tailwind-merge (`cn`) |
| 클라이언트 API | Fetch + ReadableStream (NDJSON 진행 이벤트) |

## 모듈별 불릿

### `src/app/page.tsx` — 메인 UI

- 보호자·간병인 Bearer 토큰 입력, 공고 생성·삭제를 한 페이지(`max-w-2xl` 카드 레이아웃)에 구성
- JobService 선택(`care` / `housekeeper` 미구현), 시간제·기간제·간병예정·진행중 토글로 `defaultJobPayload` 기본 JSON 자동 전환
- `useMutation`으로 생성·삭제 요청 분리, `isPending` 기반 버튼 비활성·로딩 문구 처리
- 생성 전 클라이언트 검증: 토큰 필수, JSON 파싱, `soon`/`in_progress`별 `job_start_date`·`job_end_date` 규칙
- NDJSON 진행 단계를 `createProgress` 상태로 받아 라벨·progress bar(`role="progressbar"`, `aria-live="polite"`) 표시
- 생성 성공 시 `resultSectionRef.scrollIntoView`로 결과 섹션 자동 스크롤
- 토큰·공고 유형별 시각 구분: amber(간병예정), sky(진행중), destructive(삭제)

### `src/app/providers.tsx` + `src/app/layout.tsx` — 앱 셸

- `useState(() => new QueryClient())`로 QueryClient 인스턴스를 컴포넌트 생명주기에 묶어 SSR·클라이언트 간 중복 생성 방지
- `RootLayout`에서 `Providers`로 children 래핑, `lang="ko"`·메타데이터(title/description) 설정

### `src/lib/job.ts` — 클라이언트 API

- `postJob(type, options)` 단일 함수로 `soon` / `in_progress` / `delete`를 `POST /api/job`에 위임
- 생성 요청은 응답 body를 `ReadableStream`으로 읽으며 줄 단위 NDJSON 파싱; `{ progress: string }` 이벤트마다 `onProgress` 호출
- 버퍼 잔여 줄·malformed line은 무시해 스트림 중간 끊김에 내성
- `AbortController` 35초 타임아웃; 삭제 실패 시 `AbortError`를 「요청 시간 초과」로 변환 (`page.tsx`에서 처리)

### `src/data/defaultJobPayload.ts` — 기본 페이로드

- `BASE_PAYLOAD`에 간병(care) 공고 필드(주소, 환자·계약 정보, `care_info` 등) 공통 정의
- `getDefaultTermJobPayloadString`: 시간제 — 당일 22:00 종료, `job_date` 배열
- `getDefaultDayJobPayloadString`: 기간제 — 서울 기준 다다음날 20:00 종료
- `mode: "soon"` → 오늘 19:00 시작, `"in_progress"` → 현재−1시간 정각 시작(`formatSeoulYmdHourFloor`)

### `src/lib/seoul-time.ts` — KST 날짜 유틸

- `Intl.DateTimeFormat` + `timeZone: "Asia/Seoul"`로 YMD·YMD HMS·시 정각 포맷
- `parseSeoulWallDatetimeMs`: 벽시계 문자열을 `+09:00` ISO로 해석해 ms 변환
- `normalizeJobDatetimeToHourStart`: 분·초를 `:00:00`으로 맞춤(JSON blur 시 자동 정규화)

### `src/lib/carenation/progress-config.ts` — 진행 단계 설정

- care 생성 9단계 키·한글 라벨(`CARE_PROGRESS_LABELS`), `{n}`을 `stepCount`로 치환
- `getProgressConfig(jobService)`: UI progress bar 분모·라벨 lookup
- `RESERVED_UNSUPPORTED_JOB_SERVICES`(housekeeper): UI select에는 노출, 서버에서 미구현 처리

### `src/components/ErrorMessage.tsx`

- `message`가 null/빈 문자열이면 렌더 생략, 있으면 `role="alert"` 빨간 텍스트로 표시

### `src/app/globals.css` — 디자인 토큰

- Tailwind v4 `@import "tailwindcss"`, `@theme inline`으로 shadcn 스타일 CSS 변수 매핑
- `:root` / `.dark` oklch 색상, `.page-title`·`.section-title`·`.body-secondary` 타이포 클래스

## STAR

### 1. 다단계 공고 생성 진행률 UI

**S**  
Carenation 공고 생성은 보호자·간병인 API를 9단계 순차 호출하며, 한 번의 「공고 만들기」 클릭으로 수십 초가 걸릴 수 있다. 사용자는 어느 단계에서 멈췄는지 알 수 없어 테스트·디버깅이 어렵다.

**T**  
서버가 내려주는 단계별 진행 이벤트를 UI에 실시간 반영하고, 접근성을 갖춘 진행 표시를 제공한다.

**A**  
- `src/lib/job.ts`에서 `fetch` 응답 body를 `ReadableStream`으로 읽고, 줄 단위 JSON에서 `progress` 필드를 파싱해 `onProgress(step)` 콜백 호출
- `page.tsx`의 `createJobMutation`에서 `onProgress: (step) => setCreateProgress(step)` 연결
- `progress-config.ts`의 `getProgressConfig(activeJobService)`로 단계 키→한글 라벨·`stepCount`(9) lookup
- `parseCreateProgressStep`으로 `"1.protector my-page"` 형식에서 단계 번호 추출, progress bar width·`aria-valuenow` 계산
- `role="status" aria-live="polite"`로 스크린 리더에 진행 문구 전달

**R**  
(사용자 제공)

### 2. SSR Hydration과 localStorage 토큰 지속

**S**  
보호자·간병인 access_token을 매번 붙여넣기는 테스트 반복 시 번거롭다. 다만 Next.js App Router는 서버에서 `localStorage`에 접근할 수 없어, 초기 렌더 값이 클라이언트와 달라 Hydration mismatch가 발생할 수 있다.

**T**  
토큰을 브라우저에 저장·복원하면서 서버·클라이언트 첫 렌더 HTML을 일치시킨다.

**A**  
- `useState("")`로 protector/caregiver 토큰을 항상 빈 문자열로 초기화(서버·클라이언트 동일)
- `useEffect`(마운트 1회)에서만 `localStorage.getItem`으로 복원; eslint 주석으로 의도적 set-state-in-effect 명시
- 토큰 변경 시 별도 `useEffect`로 `setItem` / 빈 값이면 `removeItem`; try/catch로 storage full·비활성 환경 무시
- storage key: `job-control:protector-token`, `job-control:caregiver-token`

**R**  
(사용자 제공)

### 3. 간병예정/진행중 클라이언트 검증과 KST 날짜 처리

**S**  
간병예정(`soon`)과 진행중(`in_progress`) 공고는 `job_start_date`·`job_end_date` 규칙이 다르고, Carenation·MySQL은 한국(서울) 기준 일정을 사용한다. 잘못된 JSON을 서버까지 보내면 다단계 API 실패 후에야 원인을 알 수 있다.

**T**  
제출 전 클라이언트에서 유형별 날짜 규칙을 검증하고, 입력 UX를 보조한다.

**A**  
- `validatePayloadForCreate(kind, payload)`: `soon`은 start > now, `in_progress`는 start ≤ 현재 시 정각·end > now
- `parseSeoulWallDatetimeMs`·`formatSeoulYmdHourFloor`로 서울 벽시계 기준 비교
- JSON textarea `onBlur`에서 `normalizeJobStartInPayloadText`로 분·초를 `:00:00` 정규화 후 텍스트 갱신
- 유형·term/day 토글 시 `buildDefaultPayloadString`으로 README 안내와 일치하는 기본 JSON 재생성

**R**  
(사용자 제공)
