# nursing-hospital 면접

## Q&A

### Q1. 이 프로젝트에서 AI를 어떻게 활용했고, 무엇이 핵심이었나?

**A.** 기획·디자인·프론트·MVP 백엔드를 Cursor AI 에이전트로 일관 생성했습니다. 핵심은 「AI에게 자유롭게 시키기」가 아니라 **입력·출력을 프로젝트에 박아 두는 것**이었습니다. 입력 측: `AGENTS.md`, `.cursor/rules/` 7종, `write-planning`·`development-workflow` 스킬, `docs/` 기획 SSOT, `docs/@agents/` 작업별 컨텍스트, `DESIGN.md` 토큰, `mockup/` HTML. 출력 검증: TDD 루프(Vitest), ESLint 9 팀 규칙, `docs/dev-logs/` 서버→UI 핸드오프. 그 결과 주문 관리처럼 복잡한 도메인은 AI가 여러 세션에 걸쳐도 같은 패턴(`useListParams`, queryOptions, 리스트 트리)으로 이어서 구현할 수 있었습니다.

### Q2. AI가 기획과 다른 코드를 쓰는 문제를 어떻게 막았나?

**A.** `development-workflow` 스킬이 첫 단계에서 기획 문서(`docs/`)를 읽고, **기획에 없거나 충돌하면 코드 작성을 중단**하고 사용자에게 질문한 뒤 기획을 먼저 고치게 합니다. 기획 자체도 `write-planning` 스킬로 `@index.md` 번호 SSOT·상대 경로 링크만 허용(내용 복붙 금지)해 문서 간 불일치를 줄입니다. 구현 단계에서는 기획 조항을 「테스트 시나리오 목록」으로 바꾼 뒤 `.test.ts`를 먼저 쓰고, 통과할 때까지 구현합니다. 예: 주문 상태 `approved`→`received` 변경 시 `docs/dev-logs/주문-목록.md`에 API·UI 영향 표를 남기고, 탭·일괄 액션·상수·테스트를 한꺼번에 맞췄습니다.

### Q3. AI로 만든 UI가 「AI 티」 나지 않게 하려면?

**A.** `nh-mockup-review.mdc`에 **「AI스럽지 않게」** 전용 단계가 있습니다. 과도한 그림자·그라디언트, 카드 안 카드, 마케팅 문구(「스마트한 재고 관리」), 설명체 플레이스홀더, 아이콘 남용, 너무 균일한 더미 숫자, 모바일 first 대형 컨트롤 등을 금지하고 DS 토큰·짧은 운영 문구·데스크톱 36px `md` 컨트롤로 대체합니다. 요양원은 `mockup/*.html`로 React 이전에 레이아웃을 검수하고, `nh-ui-conventions.md`로 필터 툴바 한 줄·테이블 정렬 같은 현장형 규칙을 product 층에 둡니다. React 쪽은 `design-system.mdc`가 컴포넌트 편집 시 토큰 하드코딩·`aria-label` 누락을 막습니다.

### Q4. `docs/@agents/`와 `AGENTS.md`는 왜 따로 뒀나?

**A.** `AGENTS.md`는 **프로젝트 전역** 온보딩 — 스택, 폴더 배치, ESLint 요약, 「리스트 쓸 때 list-page.md」 같은 상황별 문서 맵입니다. `docs/@agents/`는 **작업 유형별 슬라이스** — `list-page.md`(URL 동기화 트리), `auth.md`(토큰 갱신), `layout.md`, `server-api.md`, `msw-mock.md`. AI 컨텍스트 윈도우가 한정돼 있어 전체 `docs/`를 매번 넣을 수 없으므로, 에이전트가 지금 하는 일에 맞는 문서만 읽게 해 환각·누락을 줄입니다. AGENTS.md 57행도 「전체를 한 번에 로드하지 않고 필요한 문서만 읽는다」고 명시합니다.

### Q5. `write-planning` 스킬이 기획 AI 출력에 주는 효과는?

**A.** 번호는 `docs/@index.md`(또는 도메인별 `@index.md`)에서만 관리하고, 파일명·제목에는 번호를 넣지 않습니다. 카테고리는 도메인 폴더로 묶고, 하위 문서 2개 이상이면 폴더를 만듭니다. 다른 문서 내용은 링크로만 참조(SSOT)합니다. AI가 「주문 목록」 기획을 추가할 때 목차 번호 재정렬·링크 깨짐·중복 서술이 자주 나는데, 스킬이 이를 체크리스트화했습니다. 물류·요양원 목차가 분리(`docs/logistics/@index.md`, `docs/nursing-hospital/@index.md`)된 것도 AI가 한 파일에 모든 화면을 뒤섞지 않게 하기 위함입니다.

### Q6. development-workflow의 TDD 루프가 AI 개발에 특히 필요한 이유는?

**A.** AI는 그럴듯한 코드를 빠르게 쓰지만 **엣지 케이스·기획 조항 준수**는 약합니다. 스킬은 「테스트 시나리오 목록(기획 조항 → 검증할 것)」 작성을 필수로 하고, 테스트 환경 없으면 설치부터, **구현 전 테스트 초안**을 금지 사항으로 막습니다. 우선순위도 정해 공유 훅·queryOptions·리스트·인증·Express 라우트를 필수로 둡니다. 이 프로젝트에서는 `orderQueries.test.ts`, `OrderListPage.test.tsx`, `usePrintInvoice.test.ts` 등이 AI가 리팩터할 때 회귀를 잡는 안전망이 됐습니다.

### Q7. `docs/dev-logs/`는 AI 세션 간 어떻게 쓰였나?

**A.** 서버 구현 AI가 API·상태명을 바꾼 뒤, UI 구현 AI가 같은 맥락을 잃지 않게 **UI 수정 포인트만** 적는 핸드오프 문서입니다. `주문-목록.md` 예: `GET /counts` 응답 키 변경, `POST /confirm` 상태 체크 `approved`→`received`, 엑셀 라벨, UI에서 고칠 파일 6곳(`OrderListStatusTabs`, `OrderDataTable`, `OrderBatchActionBar` 등)을 표로 정리. development-workflow 스킬도 서버 구현 후 UI 유의사항을 dev-logs에 쓰고, UI 구현 전에 읽도록 순서를 고정합니다.

### Q8. `.cursor/plans/` 아키텍처 플랜은 AI 실행에 어떤 역할을 했나?

**A.** `프론트엔드_아키텍처_설계` 플랜이 스캐폴딩·디자인 토큰·라우팅·레이아웃·UI 라이브러리·auth·`useListParams`·api-layer·server를 todo로 쪼개 **completed/pending** 상태를 추적합니다. AI가 한 번에 전체를 구현하려다 누락하는 것을 방지하고, 기술 선택(Vite, TanStack Query v5, Zustand, RHF+Zod 등) 근거를 플랜 본문에 남겨 후속 세션에서 같은 결정을 유지합니다.

### Q9. TanStack Query queryOptions 팩토리 패턴을 선택한 이유는?

**A.** `orderQueries.list(params)`, `detail(id)`, `counts(filters)`처럼 queryKey·staleTime·queryFn을 한곳에 모읍니다. 컴포넌트는 `useQuery(orderQueries.list(queryParams))`만 호출하고, 무효화는 `orderQueries.all()` 계층 키로 통일합니다. AI가 여러 파일에 흩어진 `useQuery`를 쓰면 키 불일치로 캐시가 꼬이기 쉬운데, 팩토리가 그 실수를 줄입니다. `orders.test.ts`로 키 구조를 검증합니다.

### Q10. `useListParams`와 리스트 표준 트리는 AI 확장에 어떻게 도움이 되나?

**A.** `docs/@agents/list-page.md`에 StatusTabs → FilterBar → BatchActionBar → DataTable → Pagination 트리를 정의하고, `useListParams`가 URL 파싱·기본값 생략·필터 타입 검증을 담당합니다. `OrderListPage`가 첫 레퍼런스 구현이고, 배송·재고·정산 리스트는 기획만 있고 UI는 스텁이지만 **같은 훅·트리를 복제**하면 AI가 새 리스트를 추가할 때 패턴이 같아집니다. 북마크 URL = API 조건이라 기획·QA·AI 구현이 같은 계약을 공유합니다.

### Q11. 출고 지시서 인쇄(`usePrintInvoice`)에서 iframe을 쓰는 이유는?

**A.** PDF 새 탭은 포커스 이탈이 잦습니다. `printBlob`은 blob URL을 숨김 iframe에 넣고 `contentWindow.print()`로 현재 창 인쇄만 띄웁니다. `print()`는 non-blocking이라 Promise는 즉시 resolve하고, `OrderBatchActionBar`는 `pendingPrepareIds`를 들고 배송준비 모달을 나중에 열어 Chrome 인쇄 미리보기와 겹치지 않게 합니다. 이 동작은 AI가 주석 없이 추측하기 어려워 `usePrintInvoice.test.ts`와 주석으로 고정했습니다.

### Q12. 현재 구현 범위와 AI로 이어서 확장할 때 주의점은?

**A.** AI 워크플로 인프라·주문 도메인은 완성도가 높고, 배송·재고·정산 등은 `App.tsx` 라우트 + 기획 문서 + 스텁만 있습니다. 요양원 관리자는 `docs/nursing-hospital/` + `mockup/`까지 있고 React 미연결. 확장 시: (1) 해당 기획 md + `@agents/list-page` 또는 layout 읽기, (2) dev-logs 확인, (3) 테스트 시나리오 선작성, (4) `useListParams`·queryOptions·DataTable 재사용. 목업 추가 시 `nh-mockup-review` 4단계 필수.
