# sequence-game 면접

## 면접 Q&A

### 공통 / 아키텍처

### Q. 왜 보드·턴·승리 판정을 Firebase Functions(서버)에 두고 클라이언트는 Realtime Database 구독 중심으로 설계했나요?
A. 멀티플레이에서 턴과 카드 검증을 클라이언트에만 두면 조작·불일치가 생깁니다. `place-card`/`start-game`은 Admin SDK로 RTDB를 갱신하고, 클라이언트는 `onValue`로 같은 경로를 구독해 UI만 맞춥니다. 쓰기의 권위는 서버, 읽기·표현은 클라이언트라는 경계를 둔 이유입니다.

### Q. Jotai atom과 페이지 로컬 `useState`를 어떻게 나눴나요?
A. 로그인 유저(`userAtom`), 전역 알림(`alertMessageAtom`), 튜토리얼/모달 계열은 여러 화면에서 공유되므로 atom으로 두었습니다. 게임룸의 보드·핸드·턴처럼 해당 방 구독 스냅샷에 묶인 값은 `GamePage` 로컬 state로 두고, 구독이 끊기면 함께 사라지게 했습니다. 전역으로 올리면 방 전환 시 잔존 상태 위험이 커지기 때문입니다.

### Q. Lounge에서 RTDB 실시간 구독과 `/userRoom` HTTP API를 함께 쓰는 이유는?
A. 방 목록은 다수 유저가 동시에 보는 공개 데이터라 `rooms` 구독이 자연스럽습니다. 반면 “내가 지금 어느 방에 묶여 있는지”는 재접속·중복 참여 방지용 개인 매핑이라 `userRooms`를 API로 조회해 라운지 진입 시 기존 룸으로 보냅니다. 목록 동기화와 유저-방 소속 확인의 관심사를 나눈 구조입니다.

### client — 라우팅·딥링크

### Q. URL로 `room/:roomId`에 바로 들어왔을 때 join 흐름을 어떻게 설계했나요?
A. `useJoinRoomOnUrlAccess`가 로그인 유저와 URL `roomId`를 받으면 먼저 `/userRoom`으로 기존 소속을 확인합니다. 이미 다른/같은 방에 있으면 그 방으로 리다이렉트하고, 없으면 해당 `roomId`로 `join-room`을 시도합니다. 실패 시 API 메시지를 알림으로 띄우고 `/lounge`로 돌려 잘못된 초대·정원 초과를 UI에서 마무리합니다.

### Q. Firebase Auth(Google)와 Express `/api/login`의 `verifyIdToken`은 각각 어떤 역할인가요?
A. 클라이언트는 `signInWithPopup`으로 세션을 만들고 `userAtom`에 유저를 둡니다. Functions의 `/api/login`은 Authorization Bearer ID 토큰을 Admin으로 검증해 uid를 돌려주는 서버 측 로그인 확인 엔드포인트입니다. 실게임 API는 주로 `userId`를 body로 받는 형태라, 토큰 검증을 모든 쓰기에 강제했는지와 현재 RTDB 규칙의 넓음은 개선 포인트로 설명할 수 있습니다.

### functions — 게임 규칙

### Q. J(잭) 카드와 일반 카드 배치를 서버에서 어떻게 분기하나요?
A. `place-card`에서 먼저 턴·보유 카드·보드 존재 여부를 검사합니다. 카드에 `J`가 포함되면 무늬로 나눕니다. ♠/♥는 상대 칩 제거(이미 시퀀스인 칸·아군 칩은 거부), ♦/♣는 빈 칸에 아군 칩 자유 배치입니다. 그 외 일반 카드는 전달된 좌표에 팀색을 올립니다. 규칙 분기를 서버에 모아 클라이언트가 임의로 칩을 지우지 못하게 했습니다.

### Q. 시퀀스(5연속) 승리는 어떤 방식으로 검사하나요?
A. `checkWin`이 보드를 순회하며 팀색 기준으로 길이 5 연속을 찾고, 완성된 시퀀스 좌표를 `sequenceIndices`에 모읍니다. 해당 칸에 `isSequence`를 표시해 이후 J 제거 대상에서 보호합니다. 시퀀스 개수가 2 이상이면 `winner`와 `gameFinished`를 설정합니다. 인원별 핸드 장수·팀 교차 배정은 `start-game`에서 처리합니다.

### 트레이드오프 / 제약

### Q. `database.rules.json`이 `.read/.write: true`인데, 프론트·보안 관점에서 어떻게 설명하나요?
A. 현재 규칙은 개발 편의 중심이라 클라이언트가 경로를 알면 직접 쓰기도 가능한 상태입니다. 제품화 시에는 Auth uid 기반 규칙으로 읽기/쓰기를 제한하고, 게임 상태 변경은 Functions(Admin)만 허용하는 편이 맞습니다. 면접에서는 “서버 권위 API는 갖췄지만 RTDB 규칙은 아직 개방이라 다음 과제”라고 코드 사실과 개선안을 같이 말하면 신뢰도가 높습니다.
