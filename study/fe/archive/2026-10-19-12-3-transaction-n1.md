## 정리

### 한 줄

**트랜잭션**은 다중 쓰기를 **ACID**로 묶고 격리 수준으로 읽기 이상을 trade-off하며, **N+1**은 목록 1번 + 행마다 추가 쿼리로 FE 목록 API를 죽이므로 **join/eager/batch**로 1~2번으로 줄인다.

### 핵심

- **ACID**: **Atomicity** 전부 commit or rollback — 결제+재고. **Consistency** 제약 유지. **Isolation** 동시 tx 간 간섭. **Durability** commit 후 디스크.
- **격리**: Read Committed(기본 많음) / Repeatable Read / Serializable. ↑일수록 **phantom·non-repeatable** 방지 but **락·처리량↓**. “항상 Serializable”은 과잉.
- **데드락**: tx A가 row1→row2, B가 row2→row1 lock — **리소스 접근 순서 통일**, 짧은 tx.
- **N+1**: `SELECT * FROM posts LIMIT 20` + 각 post마다 `SELECT author WHERE id=?` → **21 queries**. GraphQL resolver·ORM lazy relation에서 흔함.
- **해결**: SQL **JOIN**, ORM `include`/`join`, **DataLoader** batch+ cache, `WHERE id IN (...)`.

### 흐름

```
[TX]
  BEGIN → debit wallet → insert order → COMMIT
  (중간 fail) → ROLLBACK → money restored

[N+1 → fix]
  posts(20) → for each load author  // bad
  → posts JOIN authors             // good
  → authors WHERE id IN (...)      // good batch
```

### 차이·함정

| 대비 | 한 줄 |
|------|--------|
| N+1 vs slow index | 쿼리 **개수** vs 한 쿼리 **cost** |
| eager vs lazy | 미리 join vs 첫 access 때 |
| tx vs saga | 단일 DB vs 분산 보상 |
| optimistic vs pessimistic lock | version vs SELECT FOR UPDATE |
| client cache vs N+1 | FE cache는 서버 쿼리 수 안 줄임 |

### 실무 연결

- React Query **한 endpoint**가 느리면 서버 N+1 — DevTools에서 **동일 API 1번**인데 TTFB 길면 쿼리 수 말고 index(12-2).
- **낙관적 UI** mutation + tx rollback — 서버 tx fail 시 FE invalidate로 되돌림.
- SSOT·일관성: tx로 서버 state 맞춘 뒤 FE Query cache invalidate.

### 면접 한 방

- **Q:** N+1이 뭐고 어떻게 고치나?
- **답:** 목록 조회 1번 후 각 row마다 연관 데이터를 또 조회해 1+N번 쿼리가 난다. join, eager loading, IN batch, DataLoader로 연관을 한두 번에 가져온다. 트랜잭션은 여러 쓰기를 한 단위로 commit/rollback할 때 쓴다.

### 통과선 스크립트

1. TX when: 다중 쓰기 all-or-nothing.
2. ACID 한 줄 each.
3. 겹리 수준 = trade-off, 항상 max 아님.
4. 데드락 = 순서 통일.
5. N+1 = 1+N, fix join/batch.
6. FE는 쿼리 수를 직접 안 보지만 latency로 체감.
