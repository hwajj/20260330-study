## 정리

### 한 줄

제네릭은 타입을 **파라미터**로 받아 호출 시점의 타입을 보존·전파하고, `extends`/`keyof`로 안전한 API(훅·유틸)의 계약을 고정한다.

### 핵심

- **`any`와의 차이**: `any`는 타입 정보를 버리고, 제네릭은 입력→출력 **관계**를 유지한다. `identity<T>(x: T): T`가 기본 감각.
- **Generic Interface**: `ApiResponse<T> { data: T }`처럼 구조는 같고 payload만 바뀌는 패턴. 리스트/상세 응답에 반복.
- **Constraint (`T extends { id: number }`)**: 내부에서 `.id` 접근이 필요하면 제약을 걸어 **최소 형태**를 보장. 제약 없으면 컴파일러가 멤버를 모른다.
- **`keyof` + 인덱싱**: `K extends keyof T` → `T[K]`. 존재하는 키만 받고 반환 타입을 정확히 맞춘다. Day 19 유틸리티 타입의 뼈대.
- **추론 vs 명시**: 인자에서 `T`가 추론되면 호출부에 `<string>`을 안 써도 된다. 훅 옵션 객체처럼 인자만으로는 부족하면 제네릭 인자를 **명시**한다.

### 흐름

```
호출부 타입 결정
  → 제네릭 파라미터 T (추론 or 명시)
  → (선택) T extends Constraint 검사
  → 본문에서 T / T[K]로 안전한 접근
  → 반환 타입에 T 전파 (관계 유지)
```

리스트 훅 감각:

```
useListParams<Filters>(schema?)
  → URL string → 파싱 → Filters 형태
  → setParams: Partial<Filters> 수준으로 부분 갱신
  → queryKey / API query에 Filters 그대로
```

### 차이·함정

| 대비 | 한 줄 |
|------|--------|
| 제네릭 vs `any` | 관계 보존 vs 검사 포기 |
| 제약 없음 vs `extends` | 멤버 접근 불가 vs 최소 shape 보장 |
| `keyof T` vs `string` | 실제 키 유니온 vs 임의 문자열(오타 허용) |
| 과도한 `as` | 제네릭으로 풀 수 있는 관계를 단언으로 우회 → 런타임 구멍 |
| 인터페이스 제네릭 vs 함수 제네릭 | 구조 재사용 vs 한 번의 호출 입출력 관계 |

### 실무 연결

- **nursing `hooks/useListParams.ts` (시그니처만)**: URL search params ↔ 페이지·필터·정렬을 동기화하는 훅. 제네릭으로 **필터 스키마 타입**을 받아 파싱·기본값 생략·enum/date 검증 결과가 그 타입으로 남게 한다. `any`로 파싱하면 북마크 URL=API 조건이라는 계약이 타입에서 끊긴다.
- W4 월 저녁: Vite+TS + RQ Provider 토이 — 리스트 파라미터를 제네릭 훅으로 잡을 준비. Week 7에서 라인 단위로 깊게 들어간다.
- 인터뷰 감각: StatusTabs→FilterBar→… 트리와 같은 패턴을 복제할 때 **시그니처가 템플릿**이 된다.

### 면접 한 방

- **Q:** 제네릭을 쓰면 `any`와 뭐가 다르고, `keyof`랑 같이 쓰는 대표 예는?
- **답:** `any`는 타입을 포기하고, 제네릭은 호출 타입을 보존해 입출력 관계를 지킨다. 예: `get<T, K extends keyof T>(obj, key): T[K]` — 있는 키만 받고 그 프로퍼티 타입을 반환. 제약(`extends`)은 본문에서 안전하게 멤버에 접근하려고 둔다.
