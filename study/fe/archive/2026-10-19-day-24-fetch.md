## 정리

### 한 줄

`fetch`는 Promise로 응답을 주고, HTTP 4xx/5xx는 reject가 아니라 **`res.ok`로 직접 판정**하며, CORS는 서버 헤더·프록시 문제이고, AbortController로 중복·언마운트 요청을 끊는다.

### 핵심

- **Promise + async/await**: `const res = await fetch(url, opts)` → `await res.json()`. 헤더 도착과 바디 파싱은 **두 단계**.
- **에러 모델**: 네트워크 실패·abort만 reject. 404/500은 Response가 오므로 `if (!res.ok) throw …`.
- **CORS**: 브라우저가 교차 Origin 응답을 JS에 넘기기 전 검사. 콘솔 CORS는 대개 **서버 Allow-*** 또는 credentials 불일치. 프론트만으로 “고치기” 어렵다.
- **Simple vs Preflight**: 단순 GET/POST 등은 본요청만. 커스텀 헤더·`application/json`·PUT/DELETE 등은 먼저 `OPTIONS`.
- **Credentials**: `credentials:'include'`면 `Allow-Origin: *` 불가 — 구체 Origin + Allow-Credentials.
- **AbortController**: `signal` 전달 후 `abort()` — 검색어 변경·언마운트·탭 전환 시 필수 감각. RQ가 대신 관리하기도 함.
- **CORS ≠ SameSite**: CORS=JS가 응답을 읽어도 되나 / SameSite=쿠키를 실을까(CSRF, Day 26).

### 흐름

```
fetch(url, { signal, headers, credentials? })
  → (필요 시) OPTIONS preflight
  → Response (status 포함, 네트워크 OK면 resolve)
  → if (!res.ok) 에러로 승격
  → await res.json()
  → UI / RQ cache
```

주말 복습 + 토이:

```
Promise then 체인 ≡ async/await
  → 리스트·detail queryFn 내부 fetch
  → 개발: baseURL '/api' + Vite proxy (same-origin)
  → abort: 키 변경 시 이전 요청 취소(또는 RQ)
```

### 차이·함정

| 대비 | 한 줄 |
|------|--------|
| 네트워크 reject vs !res.ok | 연결 실패 vs HTTP 에러 응답 |
| await fetch vs await json | 헤더·상태 vs 바디 파싱 |
| CORS vs SameSite | 응답 읽기 허용 vs 쿠키 전송 |
| Simple vs Preflight | 본요청만 vs OPTIONS 선행 |
| `*` Origin + credentials | 불가능 — 구체 Origin 필요 |
| 절대 API URL in env | 브라우저 직행 → CORS 나기 쉬움 |

### 면접 한 방

- **Q:** fetch는 404일 때 왜 catch로 안 가고, CORS·취소는?
- **답:** fetch는 네트워크 실패만 reject하고, 404도 Response로 resolve되므로 `res.ok`를 본다. `json()`은 바디 스트림이라 한 번 더 await. CORS는 서버 Allow 헤더/프록시 문제이고, 취소는 AbortController signal. credentials와 `*` Origin은 같이 못 쓴다.
