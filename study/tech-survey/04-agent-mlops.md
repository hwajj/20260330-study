## 진행

### Agent 구성

- **LLM:** 계획·자연어 추론·tool 호출 **포맷** 생성  
- **tools:** API·DB·코드 실행 등 **외부 행동** (환각 줄이고 사실·액션 분리)  
- **planning loop:** 목표까지 **반복** (실패 시 재시도·다른 tool)  
- **human approval (선택):** 결제·삭제·메일 발송 등 **되돌리기 어려운** action 전 확인

### Agent 루프

목표 → **계획** → **tool 선택·인자** → **실행** → **observation(결과)** → (메모리/대화에 적재) → 목표 달성까지 **반복** 또는 종료.

### human-in-the-loop

tool이 **비가역·규제·비용**이 크면 LLM만 믿지 않고 **사람 승인** — prompt injection·잘못된 plan으로 **자동 실행** 방지.

### MLOps 키워드

- **experiment tracking:** 하이퍼파라미터·메트릭·아티팩트 **재현** (어떤 run이 배포됐는지)  
- **model registry:** 승 promoted 모델 **버전·스테이지**(staging/prod)  
- **drift monitoring:** serving 데이터·예측 분포가 **학습 시와 달라지면** 알람·재학습  
- **data versioning:** 학습에 쓴 **데이터 스냅샷** 추적 (재현·감사)

### DevOps vs MLOps (3줄)

1. **DevOps:** 애플리케이션 **빌드·테스트·배포·인프라** — CI/CD, feature flag.  
2. **MLOps:** **데이터·학습·평가·모델 배포·모니터링** — 실험·registry·drift.  
3. **겹침:** 둘 다 CI·관측·롤백; MLOps는 **데이터/모델 품질**이 추가 축.

### 통과선 — Agent 1회 루프 **5단계**

1. **목표 입력** (user task)  
2. **계획** (다음 action)  
3. **tool 호출** (name + args)  
4. **observation** (tool 결과)  
5. **종료 또는 반복** (답 제출 / 2로)

### 4단 설명 — Agent (한계)

1. **정의:** LLM이 tool을 **연쇄 호출**하며 목표를 수행하는 패턴.  
2. **배경:** 단일 프롬프트로는 **최신·실행·다단계** 작업 한계.  
3. **구성:** LLM + tools + memory + (guardrails·approval).  
4. **한계:** tool abuse, 무한 루프, 비용·latency, 잘못된 plan.

```
[goal] → plan → act(tool) → observe → (memory) ↻ → answer
```

## 정리

```
Agent는 LLM이 사용자의 목표를 달성하기 위해 외부 도구를 호출하고, 그 결과를 확인하면서 다음 행동을 결정하는 반복적인 실행 구조이다.

Agent는 크게 LLM, Tool, Planning Loop로 구성된다. LLM은 사용자의 목표를 이해하고 다음 행동을 계획하며, Tool은 API 호출이나 DB 조회, 코드 실행처럼 LLM이 실제로 수행할 수 없는 외부 작업을 실행한다. Planning Loop는 계획하고 Tool을 호출한 뒤 결과를 확인하고, 목표가 달성될 때까지 다시 계획하는 과정을 반복한다.

Agent의 기본 흐름은 목표 입력 → 계획 → Tool 호출 → 실행 결과 확인(Observation) → 반복 또는 종료이다. 예를 들어 사용자가 "이번 달 매출이 가장 높은 상품을 알려줘"라고 하면, Agent가 매출 데이터를 조회할 계획을 세우고 DB Tool을 호출한 다음, 반환된 데이터를 확인하여 필요한 계산을 수행하고 최종 결과를 답변한다.

Human-in-the-loop는 Agent가 중요한 작업을 실행하기 전에 사람의 승인을 받도록 하는 방식이다. 결제, 파일 삭제, 메일 발송처럼 잘못 실행했을 때 피해가 크거나 되돌리기 어려운 작업은 LLM의 판단만으로 실행하지 않고 사람의 승인을 거치게 한다. 이를 통해 잘못된 계획이나 Prompt Injection 등에 의한 위험한 실행을 줄일 수 있다.

MLOps는 머신러닝 모델을 개발하고 배포한 이후에도 데이터와 모델의 상태를 지속적으로 관리하기 위한 운영 체계이다. 일반적인 DevOps가 애플리케이션의 빌드, 테스트, 배포, 운영에 초점을 둔다면, MLOps는 여기에 데이터, 모델 학습, 평가, 모델 버전 관리, 성능 모니터링, 재학습까지 포함한다.

Experiment Tracking은 머신러닝 실험에서 사용한 하이퍼파라미터, 평가 지표, 모델 등의 정보를 기록하여 어떤 조건에서 어떤 결과가 나왔는지 추적하고 재현할 수 있도록 하는 것이다.

Model Registry는 학습된 모델의 버전과 상태를 관리하는 저장소이다. 어떤 모델이 개발 중인지, 테스트 중인지, 현재 운영 중인지 등을 관리하고 필요하면 이전 버전으로 되돌릴 수 있다.

Drift Monitoring은 모델을 학습시킬 당시의 데이터와 실제 서비스에서 들어오는 데이터의 분포가 달라지는 현상을 감시하는 것이다. 실제 환경의 데이터 특성이 변화하면 모델의 성능이 떨어질 수 있으므로 이를 감지하여 재학습이나 모델 교체를 판단한다.

Data Versioning은 모델 학습에 사용한 데이터의 버전을 관리하는 것이다. 어떤 모델이 어떤 데이터로 학습되었는지를 추적할 수 있어 학습 결과를 재현하고 문제 발생 시 원인을 찾는 데 도움이 된다.

결국 이 항목의 핵심은 Agent는 "LLM이 Tool을 사용하면서 반복적으로 행동하는 구조"이고, MLOps는 "데이터와 모델을 포함한 머신러닝 생명주기를 운영하는 체계"라고 이해하면 된다.
```
